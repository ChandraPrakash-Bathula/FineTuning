# Interactive Fine-Tuning : Full Fine Tuning, LoRA, QLoRA.

A four-part lesson built on eleven real fine-tuning experiments on
`Qwen/Qwen2.5-7B-Instruct` over WikiSQL.

**Every displayed number traces to an artifact or to arithmetic on the model's own
config.** Nothing is invented, and each figure is labelled with where it came from:

| Badge | Meaning |
|---|---|
| `measured` | read from a Phase 1 artifact (`registry.json`) |
| `calculated` | derived from `config.json` or from recorded values, shown as arithmetic |
| `estimated` | a measured value times an assumption declared in `frontend/src/lib/cost.ts` |
| `recorded` | a stored model output from the probe run |
| `live` | generated by the inference backend just now |

## Run it

```bash
cd frontend && npm install && npm run dev
```

No GPU needed. The lesson, the experiment replay, the comparisons and the SQL
laboratory all read recorded artifacts, and nothing here calls a model at request
time. An optional inference backend exists (see below); the SQL lab reports
whether one is reachable, but the app runs completely without it.

## The four parts

**1 · Why fine-tune** — the knowledge gap, full fine-tuning as the obvious answer,
and the wall it hits: 76.4 GB peak memory, a 15.24 GB checkpoint per task, and only
two of four common cards able to run it.

**2 · LoRA** — an eight-step walkthrough of ΔW = BA on a real `q_proj`, the four
adapted matrices at true shapes, rank explorer, and the rank-vs-accuracy curve with
its error band.

**3 · QLoRA** — NF4 with the real 16 levels, an interactive worked example that
starts on a weight which actually quantises badly, the memory arithmetic, and the
serving-base comparison below.

**4 · Playground** — select an experiment, replay its recorded loss curve, read its
measured metrics, compare any subset on any metric, and explore all 1,000 held-out
questions.

## What the data says

All findings below are scoped to this setup: Qwen2.5-7B-Instruct, WikiSQL, one seed
(42) per run, about 56,000 training examples, and one learning rate per method
(1e-5 for full fine-tuning, 2e-4 for adapters).

**Significance is tested with paired methods.** Every variant answered the same
1,000 held-out questions, so accuracies are compared with McNemar's exact test and a
paired bootstrap (10,000 resamples), not an unpaired two-proportion test. The first
version of this project used the unpaired test, which ignores the pairing and
overstates the noise. `scripts/paired_stats.py` computes every test from the
per-question results in `frontend/public/probes` and writes
`frontend/public/paired_stats.json`.

**Every accuracy comes from the probe runs.** The evaluation run in-process right
after training stored only totals, which a paired test cannot use. The probe runs
re-generate from the checkpoints on disk and record every question, so the app,
paper and slides all report them. `scripts/registry_from_probes.py` writes them into
the frontend copy of the registry and keeps the original block as
`evaluation_at_training`. The two passes differ by up to 0.4 points per variant
(full FT 75.4% vs 75.3%), which sets a noise floor from re-generation alone.

**Full fine-tuning scored below the adapters, in this setup.** All eleven land in
75.4–78.3% execution accuracy, but the gap is not random: full fine-tuning scored
lower than all ten adapters. Averaged per question over the ten adapters, the gap is
**+2.0 points (paired sign-flip test p = 0.013, 95% interval +0.4 to +3.6)**. Single
pairs are weaker evidence: 6 of the 55 pairs reach McNemar p < 0.05 (full FT vs
QLoRA r=8: p = 0.005), but none survive a Holm correction for 55 comparisons. These
tests cover only which questions were sampled, not training noise. With one seed and
one learning rate for full fine-tuning, this is not evidence that adapters beat full
fine-tuning in general. Meanwhile costs differ by up to 707× in checkpoint size.

**Rank and quantisation made no measurable difference to accuracy.** Across all five
ranks, Cochran's Q gives p = 0.46 for LoRA and p = 0.14 for QLoRA; LoRA r=4 vs r=64:
McNemar p = 0.76. QLoRA vs LoRA at the same rank: p = 0.10–0.82.

**Serving base is part of the method.** Two probe runs exist. `regen.log` generated
all eleven against a bf16 base; `regen_q.log` re-ran the five QLoRA variants against
the 4-bit NF4 base they were trained on. The 4-bit run reproduces the registry's own
evaluation 7.5× more closely, so it is the canonical set. The bf16 run is kept
because the gap is a real result: **every rank loses accuracy on a bf16 base, 1.0
point on average (paired sign-flip test over the five adapters, p = 0.009)**. Per
rank, only r=16 reaches p < 0.05 on its own. `backend/app.py` therefore loads two
bases and puts QLoRA adapters on the 4-bit one.

**SQL text and SQL behaviour are different things.** Over 1,000 questions: 635
produce identical SQL from all eleven, 263 genuinely split, **48 produce different
SQL that is all correct**, and 54 produce different SQL that is all wrong. Counting
identical SQL too, 109 questions are missed by all eleven. Q603 is the clearest —
three different `COUNT(colN)` queries, none matching gold, all returning the gold
rows.

## Regenerating the data

```bash
python3 scripts/fetch_artifacts.py                        # registry + figures from HF
python3 scripts/build_probes.py <export-dir> <4bit-dir>    # canonical probe set
python3 scripts/check_disagreement.py                      # featured teaching cases
python3 scripts/paired_stats.py                            # paired significance tests
python3 scripts/paired_figure.py                           # accuracy figure with paired p
```

`build_probes.py` splits the exports into one shared question list plus 64K per
variant, compares every aggregate with the registry, then runs
`registry_from_probes.py`. That writes the frontend copy of the registry with probe
SQL metrics and without the superseded 25-probe blocks, so there is exactly one source
of accuracy. `data/registry.json` is never modified. To refresh only the registry copy,
run `python3 scripts/registry_from_probes.py`.

## Deploying to a Hugging Face Space

Two flavours. A write-scoped `HF_TOKEN` is needed for either.

**Static — free, and it is the whole product.** The production build is fully
self-contained: the lesson, the experiment replay, every comparison, and all 1,000
recorded questions work with no server at all.

```bash
HF_TOKEN=hf_xxx python3 scripts/deploy_space.py static <user>/<space-name>
```

Uploads 27 files, 2.3 MB, onto free CPU Basic hardware.

**Docker — runs a real backend alongside it.** FastAPI serves the built frontend
and the API on one origin, so there is no CORS to configure and no `VITE_API_BASE`
to set. This makes `/api/health` genuinely report the loaded bases and adapters
instead of "not configured," but see the note above: no UI path calls
`POST /api/run` yet, so this does not currently change what the lesson shows.

```bash
HF_TOKEN=hf_xxx python3 scripts/deploy_space.py docker <user>/<space-name>
```

Then pick hardware under the Space's Settings:

| `LOAD_BASES` | Serves | Minimum hardware |
|---|---|---|
| `qlora` | the five QLoRA adapters | Nvidia T4 — 16 GB |
| `both` (default) | LoRA + QLoRA | Nvidia L4 / A10G — 24 GB |
| `both` + `LOAD_FULL_FT=1` | all eleven | Nvidia L40S — 48 GB (~35 GB used) |

The bases warm up in a background thread at startup, so the ~16 GB download and
three model loads happen before the first request instead of during it.
`/api/health` reports `models: cold | loading | ready | error | no_gpu`, and the UI
shows that state rather than hanging.

Free CPU Basic has 16 GB of RAM and no CUDA, so it cannot host live inference —
but a Docker Space on CPU still serves the whole lesson and reports live inference
as unavailable.

## Design decisions

**The matrix figures are geometrically real.** Shapes come from the model's
`config.json`: hidden 3,584, 28 layers, and grouped-query attention that makes
`k_proj`/`v_proj` output 512 features rather than 3,584. The parameter counts that
fall out reproduce `registry.json` exactly (r=4 → 2,523,136; r=64 → 40,370,176).
Matrices in one figure share a pixels-per-element unit, so a dimension two matrices
have in common is drawn at the same size. Where a figure cannot be to scale — a
rank-4 sliver beside a 3,584-wide matrix is under a pixel — it says so and pairs
itself with a to-scale bar.

**Colour.** Method carries hue, rank carries lightness. Colour binds to the variant,
never to its position in a selection, so filtering never repaints the survivors.
Every value in `frontend/src/lib/palette.ts` passed the dataviz validator in both themes.

**Units are the registry's.** Decimal GB/MB, so the app shows 76.4 GB, not 71.2 GiB.

**Loss is on a log axis.** QLoRA r=64 genuinely spikes to 5.28 at step 3,025; on a
linear axis that one point flattens two orders of magnitude of convergence. Spikes
are preserved, never smoothed.

**SQL diffing is case-sensitive inside string literals.** `'CitV'` vs `'CITV'` is a
real miss; keywords stay case-insensitive.

## The inference backend (not wired into the UI)

`backend/app.py` is a standalone FastAPI service that can load the real bases and
adapters and answer a question live, rather than replaying a recorded one:

```bash
pip install -r backend/requirements.txt
uvicorn backend.app:app --port 8000        # LOAD_FULL_FT=1 to add full_ft
```

```
GET  /api/health     GET /api/registry    GET /api/examples    POST /api/run
```

Two bases load once — bf16 for LoRA, 4-bit NF4 for QLoRA — and adapters switch with
`set_adapter()` rather than reloading a 7B model per request.

**Hardware required.** The bf16 base is 15.2 GB of weights, and the QLoRA path needs
bitsandbytes, which is CUDA-only. So this needs a CUDA GPU with ≥16 GB of VRAM
(≥32 GB to also load `full_ft`). It will not run on Apple Silicon, and it will not
run on a machine with 8 GB of memory.

**The frontend currently only shows whether this is reachable, nothing more.** The
SQL lab polls `/api/health` (via `VITE_API_BASE`, or same origin on the Docker
Space) and reports the connection state, but every answer it displays still comes
from the recorded Phase 1 probe run: no UI path calls `POST /api/run`. Everything
else in this project runs anywhere, on recorded artifacts alone, which is the point:
a static deployment is only files on a CDN and can never run a 7B model itself.

**Not verified:** the backend has never been executed against a live request —
there is no GPU on this machine. It parses and the adapter-switching structure is
right, but treat it as untested.

### If you want to actually run it

1. **Get a real CUDA GPU.** Nothing here can run it, not this Mac, not a static
   site. Cheapest paths: a free Colab T4 (works with `LOAD_BASES=qlora`), a rented
   GPU (RunPod, Lambda, vast.ai), or the HF Docker Space deployment above with GPU
   hardware selected in Settings.
2. **Run `backend/app.py` on that machine** (`uvicorn backend.app:app`). It already
   loads Qwen2.5-7B-Instruct and the adapters; this part hasn't changed.
3. **Expose it publicly** if it is not already: a cloudflared or ngrok tunnel for a
   rented box, or nothing extra for a Docker Space, which is public by default.
4. **Wire the frontend back up.** This is the part that is actually missing right
   now. When the "Ask them something new" UI was removed, so was the only code path
   that called `POST /api/run` (`runLive` in `frontend/src/lib/backend.ts`). Today,
   connecting a working backend only flips the SQL lab's status message; nothing
   calls it. Getting real live answers back means rebuilding a UI action for it:
   either that old custom-table flow, or something smaller like a "regenerate live"
   button next to a held-out SQL lab question.
5. **Test it on that real GPU** before trusting it for anything. The backend has
   never been exercised end to end; that is still the honest gap noted above.
