# Interactive Fine-Tuning : Full Fine Tuning, LoRA, QLoRA.

A four-part lesson built on eleven real fine-tuning experiments on
`Qwen/Qwen2.5-7B-Instruct` over WikiSQL.

**Every displayed number traces to an artifact or to arithmetic on the model's own
config.** Nothing is invented, and each figure is labelled with where it came from:

| Badge | Meaning |
|---|---|
| `measured` | read from a Phase 1 artifact (`registry.json`) |
| `calculated` | derived from `config.json` or from recorded values, shown as arithmetic |
| `estimated` | a measured value times an assumption declared in `frontend/src/lib/cost.ts` |
| `recorded` | a stored model output from the probe run |
| `live` | generated by the inference backend just now |

## Run it

```bash
cd frontend && npm install && npm run dev
```

No GPU needed. The lesson, the experiment replay, the comparisons and the SQL
laboratory all read recorded artifacts. Only live inference needs the backend, and
the app says so plainly when it is not running.

## The four parts

**1 · Why fine-tune** — the knowledge gap, full fine-tuning as the obvious answer,
and the wall it hits: 76.4 GB peak memory, a 15.24 GB checkpoint per task, and only
two of four common cards able to run it.

**2 · LoRA** — an eight-step walkthrough of ΔW = BA on a real `q_proj`, the four
adapted matrices at true shapes, rank explorer, and the rank-vs-accuracy curve with
its error band.

**3 · QLoRA** — NF4 with the real 16 levels, an interactive worked example that
starts on a weight which actually quantises badly, the memory arithmetic, and the
serving-base comparison below.

**4 · Playground** — select an experiment, replay its recorded loss curve, read its
measured metrics, compare any subset on any metric, and explore all 1,000 held-out
questions.

## What the data says

**Accuracy is flat.** All eleven land in 75.3–78.4% execution accuracy with a
standard error of ±1.3 points on 1,000 examples — statistically indistinguishable.
Costs differ by up to 707× in checkpoint size. The app draws the error band
explicitly and states that the accuracy chart is not a ranking.

**Serving base is part of the method.** Two probe runs exist. `regen.log` generated
all eleven against a bf16 base; `regen_q.log` re-ran the five QLoRA variants against
the 4-bit NF4 base they were trained on. The 4-bit run reproduces the registry's own
evaluation 7.5× more closely, so it is the canonical set. The bf16 run is kept
because the gap is a real result: **every rank loses accuracy on a bf16 base, about
1.0 point on average**, while LoRA and full fine-tuning drift only 0.17 points in
both directions. `backend/app.py` therefore loads two bases and puts QLoRA adapters
on the 4-bit one.

**SQL text and SQL behaviour are different things.** Over 1,000 questions: 635
produce identical SQL from all eleven, 263 genuinely split, **48 produce different
SQL that is all correct**, and 54 are missed by all eleven. Q603 is the clearest —
three different `COUNT(colN)` queries, none matching gold, all returning the gold
rows.

## Regenerating the data

```bash
python3 scripts/fetch_artifacts.py                        # registry + figures from HF
python3 scripts/build_probes.py <export-dir> <4bit-dir>    # canonical probe set
python3 scripts/check_disagreement.py                      # featured teaching cases
```

`build_probes.py` splits the exports into one shared question list plus 64K per
variant, validates every aggregate against the registry, and strips the superseded
25-probe block from the frontend copy of the registry so there is exactly one source of
probe truth (624K → 213K).

## Deploying to a Hugging Face Space

Two flavours. A write-scoped `HF_TOKEN` is needed for either.

**Static — free, and it is most of the product.** The production build is fully
self-contained: the lesson, the experiment replay, every comparison, and all 1,000
recorded questions work with no server at all. Only asking a *new* question needs a GPU.

```bash
HF_TOKEN=hf_xxx python3 scripts/deploy_space.py static <user>/<space-name>
```

Uploads 27 files, 2.3 MB, onto free CPU Basic hardware.

**Docker — adds live inference.** FastAPI serves the built frontend and the API on
one origin, so there is no CORS to configure and no `VITE_API_BASE` to set.

```bash
HF_TOKEN=hf_xxx python3 scripts/deploy_space.py docker <user>/<space-name>
```

Then pick hardware under the Space's Settings:

| `LOAD_BASES` | Serves | Minimum hardware |
|---|---|---|
| `qlora` | the five QLoRA adapters | Nvidia T4 — 16 GB |
| `both` (default) | LoRA + QLoRA | Nvidia L4 / A10G — 24 GB |
| `both` + `LOAD_FULL_FT=1` | all eleven | Nvidia L40S — 48 GB (~35 GB used) |

The bases warm up in a background thread at startup, so the ~16 GB download and
three model loads happen before the first request instead of during it.
`/api/health` reports `models: cold | loading | ready | error | no_gpu`, and the UI
shows that state rather than hanging.

Free CPU Basic has 16 GB of RAM and no CUDA, so it cannot host live inference —
but a Docker Space on CPU still serves the whole lesson and reports live inference
as unavailable.

## Design decisions

**The matrix figures are geometrically real.** Shapes come from the model's
`config.json`: hidden 3,584, 28 layers, and grouped-query attention that makes
`k_proj`/`v_proj` output 512 features rather than 3,584. The parameter counts that
fall out reproduce `registry.json` exactly (r=4 → 2,523,136; r=64 → 40,370,176).
Matrices in one figure share a pixels-per-element unit, so a dimension two matrices
have in common is drawn at the same size. Where a figure cannot be to scale — a
rank-4 sliver beside a 3,584-wide matrix is under a pixel — it says so and pairs
itself with a to-scale bar.

**Colour.** Method carries hue, rank carries lightness. Colour binds to the variant,
never to its position in a selection, so filtering never repaints the survivors.
Every value in `frontend/src/lib/palette.ts` passed the dataviz validator in both themes.

**Units are the registry's.** Decimal GB/MB, so the app shows 76.4 GB, not 71.2 GiB.

**Loss is on a log axis.** QLoRA r=64 genuinely spikes to 5.28 at step 3,025; on a
linear axis that one point flattens two orders of magnitude of convergence. Spikes
are preserved, never smoothed.

**SQL diffing is case-sensitive inside string literals.** `'CitV'` vs `'CITV'` is a
real miss; keywords stay case-insensitive.

## Live inference (optional)

**Hardware required.** The bf16 base is 15.2 GB of weights, and the QLoRA path needs
bitsandbytes, which is CUDA-only. So this needs a CUDA GPU with ≥16 GB of VRAM
(≥32 GB to also load `full_ft`). It will not run on Apple Silicon, and it will not
run on a machine with 8 GB of memory. Everything else in this project runs anywhere.

```bash
pip install -r backend/requirements.txt
uvicorn backend.app:app --port 8000        # LOAD_FULL_FT=1 to add full_ft
```

To point the frontend at a backend running elsewhere (a rented GPU, a tunnelled
Colab), set `VITE_API_BASE` before starting the dev server:

```bash
VITE_API_BASE=https://your-gpu-host npm run dev
```

```
GET  /api/health     GET /api/registry    GET /api/examples    POST /api/run
```

Two bases load once — bf16 for LoRA, 4-bit NF4 for QLoRA — and adapters switch with
`set_adapter()` rather than reloading a 7B model per request. A held-out example has
gold SQL and is scoreable; a custom question returns `scoreable: false` and the UI
must show the query and rows without a verdict.

**Not verified:** the backend has never been executed — there is no GPU on this
machine. It parses and the adapter-switching structure is right, but treat first
run as untested.
